# Files

## TL;DR — the SDK2 file model

1. **No server changes.** Keep `filenode` as a dumb, specialized, refcounted block heap. Do **not** push for "files as a native any-sync data type" — merging bulk binary into a tree-sync protocol chokes metadata sync behind gigabytes of video. The whole design lives in the SDK.
2. **Two tiers, by size:**
   - **Micro-files (< 32 KB)** — envelope-encrypted bytes embedded directly in the owning record. No `fileId`, no lifecycle, no dedup, no filenode. They live and die with their owner.
   - **Real files (≥ 32 KB)** — chunked, envelope-encrypted, pushed to filenode; one lightweight record in a space-level `files` system collection. **Not** a full any-sync object.
3. **Envelope encryption** (keep what anytype already does right): random per-file key encrypts the bytes → stable ciphertext → stable CID forever. The random key is wrapped under the space read key and stored in the file record. ACL rotation re-encrypts only the tiny wrapped key, never the blob.
4. **The `files` dataset record is the single source of truth.** Sync status is a declarative state field on it. Kill the separate persistent filesync queue.
5. **GC is two-phase epoch mark-and-sweep** with a grace period. No CRDT refcounters (that's refcount-hell). No distributed coordination.
6. **Thumbnails/variants are generated by the host OS, not Go.** One file record holds many variants.

This supersedes the earlier "files-as-first-class in any-sync, defer to v1.1" direction (kept at the bottom for history).

## What's actually below us (verified against the repos)

### any-sync `commonfile` (client chunking)
- 1 MB chunks, UnixFS balanced merkledag, **CIDv1 + SHA2-256**, codec `dag-pb`.
- **Does NO encryption.** Caller encrypts bytes *before* chunking, so **the CID is the hash of ciphertext**.
- `BlockStore`: `Get / GetMany / Add / Delete` over `blocks.Block`. `spaceId`/`fileId` flow via context.

### filenode (server)
- Stores only encrypted blocks; **zero-knowledge** of plaintext (it never re-hashes; it trusts the client's CID).
- Per-CID refcount, **dual-scoped** (per-space + per-account/"group"). Block GC'd only when refs hit zero; actual byte deletion is coordinator-driven.
- **ACL-aware:** validates `CanWrite` against the space ACL before accepting a push (`ErrForbidden` otherwise).
- Two-tier quota (account + optional per-space isolation), `ErrLimitExceed`.
- **`fileId` is distinct from CID.** The binding primitive is `BlocksBind(spaceId, fileId, []cid)`; teardown is `FilesDelete(spaceId, []fileId)`. `BlocksCheck(spaceId, []cid)` → `NotExists / Exists(account-wide) / ExistsInSpace`.
- S3 (bytes) + Redis (index).
- RPCs: `BlockGet`, `BlockPush(Many)`, `BlocksCheck`, `BlocksBind`, `FilesDelete`, `FilesInfo`, `FilesGet`, `SpaceInfo`, `AccountInfo`, quota setters, `Check`.

### What anytype-heart does today (the bar to beat)
- Every file — even a 2 KB icon — is a **full first-class object** + a filenode upload.
- Images = **5 separate variant sub-DAGs** (original/large/small/thumbnail/exif), each its own encrypted tree + key.
- **Envelope encryption already exists and is correct:** random per-file/per-variant AES-CFB key; the keys **sync with the object** (FileKeys ride in the object's changes, wrapped under the space key). The local `objectStore.AddFileKeys` table is only a fast-lookup cache, *not* the source of truth.
- Dedup: client-side, by plaintext/variant SHA-256 checksum. Random keys mean **no cross-user server dedup** (different ciphertext → different CID).
- **Sync status is a separate state machine** (`Queued→Syncing→Synced/Limited`) backed by a persistent `filesync/queue` collection, updated by async callbacks. **This is the documented root of most file bugs** — the object state and the filenode block state drift.

**The honest conclusion:** the *cryptography* anytype uses is fine. The pain is **structural** — five DAGs per image, a full object per icon, and a second consistency system (the queue + key cache) that drifts from the object. SDK2 fixes the structure, keeps the crypto.

## Design

### Principle: filenode is a dumb byte heap; the CRDT/dataset is the only source of truth
Drift happens because today the object and filenode are treated as peers coordinated by a third system (the queue). Instead: the **`files` dataset record is the heap pointer**, filenode is the heap. There is exactly one source of truth and one place state is reconciled.

### Tier 1 — Micro-files (< 32 KB): owned bytes, no entity
A note's 18 KB cover, an EXIF blob, an extreme thumbnail:
- SDK envelope-encrypts the bytes **once**, base64s them, stores them as a value field **directly on the owning record** (e.g. `note.cover_bytes`).
- **No `fileId`, no `files` record, no status, no filenode, no dedup, no GC.** The bytes live and die with their owner. Duplicate the note → duplicate the bytes.
- Trade-off accepted explicitly: the same 18 KB icon reused in 10 notes costs 180 KB. That is *infinitely* cheaper than distributed refcounting for UI assets. **Take that trade every time.**
- **Rule of thumb: if it goes to filenode it gets a `fileId` and a `files` record; otherwise it's just a value property.**

Why **not** the KV store for inline bytes: the per-space KV primitive derives its at-rest key from the space read key and **re-encrypts on every ACL rotation**. Putting binaries there means a single member leaving forces instant re-encryption + re-sync of every inline blob — a sync spike + battery drain exactly at membership-change time. Inlining into the record (envelope-encrypted under a random key wrapped once) keeps blobs out of the rotation path. **Keep binaries out of the KV store.**

### Tier 2 — Real files (≥ 32 KB): a `files` system collection record + filenode
A single **space-level system collection `files`**, one record per logical file. Objects reference it by `fileId` string (`note.cover = "<fileId>"`). Space-level (not co-located on the owning object) because the declarative sync worker needs one canonical manifest to scan, and because a real file is genuinely a shared entity.

```jsonc
// collection: files  (space-level system collection)
{
  "id": "file_uuid",                 // fileId — client-minted UUIDv4 (PK)
  "plaintextHash": "sha256-…",       // secondary index, intra-space dedup only
  "status": "available",             // declarative sync state (see below)
  "orphanTs": null,                  // set when GC marks it PENDING_DELETE
  "variants": {
    "original":  { "rootCID": "bafy…", "wrappedKey": "…", "size": 4000000, "mime": "image/jpeg", "w": 4032, "h": 3024 },
    "thumbnail": { "inlinePayload": "base64…", "wrappedKey": "…" }   // a variant MAY be inline even when the file is filenode-backed
  }
}
```

### Encryption — envelope, keep it
1. Random symmetric key **per file** (per variant). Encrypt chunks with it → **stable ciphertext → stable CID forever.**
2. Wrap that random key under the **current space read key**; store the wrapped key in the variant payload.
3. On ACL rotation: re-wrap only the tiny `wrappedKey` records inside the CRDT. **The blob on filenode is never touched.** An evicted member can no longer unwrap → loses access to future reads.

Do **not** derive file keys directly from the read key: that ties the *ciphertext* to the read key, so rotation would force re-encrypting and re-uploading every blob (CID changes). Envelope decouples blob lifetime from key lifetime — this is the single most important crypto decision and anytype already gets it right.

Do **not** use convergent encryption (key = hash of plaintext) for cross-user dedup: it enables confirmation-of-file attacks and weakens E2EE. Not worth it (see Dedup).

### Three identifiers, collapsed
| id | role | where |
|---|---|---|
| `fileId` | logical id; **also** the filenode binding id (`BlocksBind(fileId)`) | UUIDv4, PK of the `files` record |
| `plaintextHash` | intra-space dedup key | secondary index on the `files` record |
| `rootCID` | network fetch address of an encrypted variant | value inside `variants[*]` |

One UUID bridges SDK ↔ filenode; the hash is just an index; the CID is just an address.

### Declarative sync — one state machine, no queue
`status` on the `files` record is the whole story. The "queue" is `SELECT * FROM files WHERE status = …`.

- `pending_upload` → worker pushes blocks (`BlockPushMany` + `BlocksBind`) → `available`.
- `available` but a read finds blocks missing on filenode → worker downgrades to `pending_upload` and recovers. (Self-healing replaces anytype's unrecoverable `MissingBlocks`.)
- Quota hit → `limited`; retried when `SpaceInfo` shows headroom.
- Offline create: CID is computable immediately (we have bytes + the key we just minted), so the record is fully valid offline at `pending_upload`; the worker drains it on reconnect.
- Delete → `pending_delete` (see GC), never an immediate filenode call.

One source of truth, one error surface. This folds into the general **Sync Status** subsystem (`docs/09`) rather than a parallel file-status system.

### Garbage collection — two-phase epoch mark-and-sweep
No CRDT refcounters (concurrent offline ± a split-brain delete = premature deletion = corruption). No immortal files (users expect quota to drop when they delete a 2 GB video). Instead:

1. **Mark (local):** worker queries the local DB for `files` records whose `fileId` appears in **no** object reference field.
2. **Tombstone, don't delete:** set `status = pending_delete`, stamp `orphanTs = now`.
3. **Rescue via convergence:** if a CRDT sync later lands a new reference to that file, an on-write hook flips it back to `available`. This absorbs the **premature-deletion race** (Node B sweeps before Node A's referencing change has synced).
4. **Act (after grace):** worker deletes `WHERE status = pending_delete AND orphanTs < now − GRACE` (e.g. 7 days, sized to the max tolerated offline partition): `FilesDelete` on filenode, drop local blocks, drop the `files` record.

Idempotent (double `FilesDelete` is harmless), purely local index scans, no distributed coordination, time as the shock-absorber for offline partitions. This **severs the filenode lifecycle from the CRDT object lifecycle** — the two-systems problem disappears.

Known cost: deletion is eventually-consistent and storage is reclaimed lazily (grace-period delayed). Accepted.

### Thumbnails / variants
- **The Go SDK does NOT decode/resize images.** It's CPU/memory heavy and can't reach the hardware media pipelines on iOS/Android. Expose a host hook:
  ```go
  type MediaProcessor interface {
      // host (Swift/Kotlin/web) decodes, resizes, returns variant bytes
      GenerateVariants(ctx, raw []byte, mime string) (map[VariantKind][]byte, error)
  }
  ```
- **One file record, many variants** (the `variants` map above) — not five DAGs. All variants share one `fileId` and one lifecycle. A small variant (thumbnail) MAY be `inlinePayload` even when `original` is `rootCID` on filenode, so the UI renders instantly offline while the full image streams on demand.

### Dedup — intra-space, client-side, pre-sync only
- Before creating a file, hash the plaintext and query the local `files` collection by `plaintextHash`. Hit → reuse the existing record's `fileId`/blocks/wrapped key; **no filenode interaction, no crypto compromise.** Covers the real cases (same image dropped in 3 notes, re-uploaded avatar).
- **No cross-user / cross-space server dedup.** Envelope's random keys mean different users → different ciphertext → different CIDs. Recovering server dedup requires convergent encryption (leaks). Not worth it.
- **Accept offline-concurrent duplication:** two offline devices adding the same image mint two keys → two CIDs → two filenode entries that never merge. Probability is ~0; the fix (post-sync convergence resolver that picks a winner, deletes the loser's blocks, rewrites references) is weeks of bug-prone distributed code to save ~MBs. **Do not build it.**

### Why not "files as a first-class any-sync type"
Rejected. State-sync protocols optimize for tiny, causally-linked, fully-replicated mutations; file protocols optimize for large-block streaming, partial/on-demand replication, CDN caching. Forcing files into any-sync chokes text/metadata sync behind bulk binary and needs an expensive cross-team server change for ~0 product benefit over the SDK-only design. **Keep filenode separate; hide it behind the SDK.**

## Sketched SDK API

```go
// Within a space
type Files interface {
    // Add streams bytes in. Host-supplied variants are optional.
    // Returns immediately with a fileId; CID is known at once, upload is async.
    Add(ctx, reader io.Reader, opts AddOpts) (FileRef, error)

    // Open streams a variant out (fetches/decrypts on demand).
    Open(ctx, fileId string, variant VariantKind) (io.ReadSeekCloser, error)

    // Ref/Has/Status — declarative state from the files record.
    Get(ctx, fileId string) (FileRecord, error)
    // Deletion is a dereference; actual filenode delete is GC's job.
}

type AddOpts struct {
    Variants map[VariantKind][]byte // from MediaProcessor, optional
    Mime     string
}

type FileRef struct {
    FileId string // store this string on your object; "" + inline for micro-files
}
```

- Micro-file path is internal: if `len(bytes) < InlineThreshold (32 KB)` and the caller asks to inline, the SDK envelope-encrypts and hands the value back to embed on the owning record — no `Files.Add`, no `fileId`.
- References in records are plain `fileId` strings (real files) or inline byte fields (micro-files).

## Open questions / decisions to confirm in implementation
1. **Inline threshold (32 KB):** confirm against real asset-size histograms. The number trades record bloat vs filenode round-trips.
2. **`files` schema as a hardcoded SDK system dataset** (like `objects`/`members`) — confirm it's registered the same way, with a handler enforcing the declarative state field.
3. **Reference discovery for mark-and-sweep:** how does the GC worker enumerate "all fileId references across all objects" efficiently? Needs an index of file-typed fields (a `_refs` index, or a convention that file references live at known paths / a declared `x-kind:file` property kind).
4. **Grace period** (7 days?) — tie to the max supported offline partition; expose as config.
5. **Rescue hook wiring:** the on-write trigger that flips `pending_delete → available` when a reference re-appears post-sync — where does it live relative to the apply path / subscription engine?
6. **Wrapped-key rotation mechanics:** who walks the `files` collection re-wrapping keys on ACL read-key rotation, and is it batched with the existing rotation flow?
7. **`MediaProcessor` boundary** for gomobile/wasm — interface shape that survives the FFI to Swift/Kotlin/JS.
8. **Variant kinds catalog** (original/large/small/thumbnail/exif/poster…) — fixed enum vs open string.

## Source files (for reference)
- `any-sync/commonfile/fileservice/` — IPLD chunking / CID (reuse as-is).
- `any-sync/commonfile/fileproto/` — filenode dRPC (`BlocksBind`/`FilesDelete`/`BlocksCheck` are the primitives we drive).
- `any-sync-filenode/index/` — server refcount/quota model (we cooperate with it, don't replace it).
- `any-sync/commonspace/object/keyvalue/` — KV store (deliberately NOT used for binaries — rotation cost).

## Dependencies
- **Space** — files live in a space; ACL/quota/encryption inherited.
- **Data structure / datasets** — `files` is a space-level system collection; references are `fileId` value fields.
- **Sync status (`docs/09`)** — file `status` is part of the general sync-status surface, not a parallel system.
- **filenode** — unchanged; driven via `commonfile` RPC. No new server data type required.

## History (superseded direction)

The original draft proposed making files a first-class any-sync data type (move blocks into space sync, kill filenode, "one sync system") and deferring all file support to SDK v1.1. That is now rejected: it needs an expensive cross-team server change, mismatches state-sync vs block-sync workloads, and an SDK-only design (above) gets the same product wins with zero server changes. The structural fixes (tiered inline/filenode, one-record-many-variants, declarative state, epoch GC) — not a new protocol — are what beat anytype-heart.
