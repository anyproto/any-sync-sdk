# Files

## TL;DR — the SDK2 file model

1. **No server changes.** Keep `filenode` as a dumb, specialized, refcounted block heap. Do **not** push for "files as a native any-sync data type" — merging bulk binary into a tree-sync protocol chokes metadata sync behind gigabytes of video. The whole design lives in the SDK.
2. **Payloads are a per-object `payloads` dataset, materialized into a common collection.** Each object optionally owns a **`payloads` dataset** (a page with images keeps them there) — synced, owned 1:1, tombstoned with the object. Each object's payload writes **materialize into one common space-level `payloads` collection via the Controller's shared-collection override — exactly how object properties materialize into the `objects` collection** — giving the upload/GC/dedup workers one convergent place to scan. Two physical tiers by size:
   - **Micro-payload (< 32 KB)** — envelope-encrypted bytes inline in the payload row. No `fileId`, no filenode.
   - **Real payload (≥ 32 KB)** — chunked, envelope-encrypted, pushed to filenode; the row carries `fileId` + variants + wrapped key + status.
3. **Envelope encryption** (keep what anytype already does right): random per-file key encrypts the bytes → stable ciphertext → stable CID forever. Wrap the key under the space read key. ACL rotation re-wraps only the tiny key, never the blob. **Reuse the same key for identical plaintext** (found via `plaintextHash`) so identical content yields identical CIDs.
4. **`fileId` is SDK-minted and decoupled from the CID** (heart uses `fileId = root CID`). The same blocks can be bound under many fileIds; **filenode refcounts blocks per-CID and does server-side GC for us** (verified in code, below).
5. **The `payloads` row is the single source of truth.** Sync status is a declarative state field. Kill the separate persistent filesync queue.
6. **No distributed mark-and-sweep.** 1:1 ownership + the CRDT causal DAG make deletion safe: object tombstoned → its `payloads` rows die with it → `FilesDelete(fileId)` → filenode decrements. **Local** block GC is a cheap `count(*)` over the index, not a network op.
7. **Thumbnails/variants are generated by the host OS, not Go.** One payload row holds many variants.
8. **Local blocks live in one shared (account-wide) `blocks.db`**, separate from the fast-path CRDT/query any-store DB, rows tagged by `spaceId` so space deletion is a scan-and-delete.

This supersedes the earlier "files-as-first-class in any-sync, defer to v1.1" direction (kept at the bottom for history).

## What's actually below us (verified against the repos)

### any-sync `commonfile` (client chunking)
- 1 MB chunks, UnixFS balanced merkledag, **CIDv1 + SHA2-256**, codec `dag-pb`.
- **Does NO encryption.** Caller encrypts bytes *before* chunking, so **the CID is the hash of ciphertext**.
- `BlockStore`: `Get / GetMany / Add / Delete` over `blocks.Block`. `spaceId`/`fileId` flow via context.

### filenode (server)
- Stores only encrypted blocks; **zero-knowledge** of plaintext (it never re-hashes; it trusts the client's CID).
- Per-CID refcount, **dual-scoped** (per-space + per-account/"group"). Block GC'd only when refs hit zero; actual byte deletion is coordinator-driven.
- **ACL-aware:** validates `CanWrite` against the space ACL before accepting a push (`ErrForbidden` otherwise).
- Two-tier quota (account + optional per-space isolation), `ErrLimitExceed`.
- **`fileId` is distinct from CID.** Bind primitive `BlocksBind(spaceId, fileId, []cid)`; teardown `FilesDelete(spaceId, []fileId)`; `BlocksCheck(spaceId, []cid)` → `NotExists / Exists / ExistsInSpace`.
- S3 (bytes) + Redis (index).

### Verified filenode primitives (the design rests on these — confirmed in `any-sync-filenode`)
1. **`FilesDelete` is idempotent per fileId.** Deleting an unknown/already-deleted fileId is a no-op (`getFileEntry` → `isNewFile`), and a CID's refcount is decremented exactly once per binding fileId (`index/unbind.go:24-36`, `index/entry.go:31-48`). Two devices issuing `FilesDelete(sameFileId)` is safe.
2. **`BlocksBind` accepts already-stored CIDs without re-pushing bytes** — it just increments refcounts (`index/bind.go:20-44`, `filenode/filenode.go:163-173`). This is the dedup fast path. **Caveat (load-bearing):** if a CID exists *nowhere* on the server, `BlocksBind` returns **`ErrCidsNotExist`** — so after a server-side block delete you **must re-push from local bytes**. That is exactly the network-ordering invariant below.
3. **Refcount is per-(space, cid) counting distinct binding fileIds.** `fileId_A`+`fileId_B` on CID X → refcount 2; `FilesDelete(A)` → 1 (block survives), `FilesDelete(B)` → 0 (eligible). Double-binding the same CID under the *same* fileId does **not** double-count (`index/bind.go:33-39`; tests `index/unbind_test.go:51-87`, `index/bind_test.go:78-101`). This is precisely the cross-content sharing the design relies on.

### What anytype-heart does today (the bar to beat)
- Every file — even a 2 KB icon — is a **full first-class object** + a filenode upload. `fileId = root CID` (content-derived, so identical content can't exist as two named entities).
- Images = **5 separate variant sub-DAGs**, each its own encrypted tree + key.
- **Envelope encryption already exists and is correct:** random per-variant AES-CFB key; the keys **sync with the object** (FileKeys ride in the changes, wrapped under the space key). The local `objectStore.AddFileKeys` table is only a fast-lookup cache, *not* the source of truth.
- Dedup: client-side by SHA-256 checksum. Random keys → **no cross-user server dedup**.
- **Sync status is a separate state machine** + persistent `filesync/queue`, updated by async callbacks — **the documented root of most file bugs** (object state and filenode block state drift).

**The honest conclusion:** the *cryptography* anytype uses is fine. The pain is **structural** — five DAGs per image, a full object per icon, and a second consistency system that drifts. SDK2 fixes the structure, keeps the crypto.

## Design

### Principle: filenode is a dumb byte heap; the CRDT/dataset is the only source of truth
Drift happens because today the object and filenode are coordinated by a third system (the queue). Instead: the **`payloads` row is the heap pointer**, filenode is the heap. One source of truth, one place state reconciles.

### Where payloads live — per-object dataset + local space index
- **Source of truth: a per-object `payloads` dataset.** An object opts in only if it has payloads (a page with images stores them there). It's a normal dataset written through the object's CRDT — so it's **synced, owned 1:1, and tombstoned together with the object** (delete the object → its `payloads` rows are tombstoned with it; sticky, convergent — see `05a-crdt-spec §3.4/§5.7`). This is what makes lifecycle safety free.
- **Scan surface: a common `payloads` collection, materialized like properties.** Wire the per-object `payloads` dataset through the Controller's **shared-collection override** — the same mechanism that coalesces every object's property writes into the one `objects` collection (`SystemPropertiesHandler`; see `06-data-structure`). Each object's payload changes materialize, keyed by payload id, into one common space-level `payloads` collection. The upload worker, GC, and dedup scan that single collection. Because it's produced by *applying the same synced CRDT changes on every peer*, it's **convergent by construction** — not a hand-maintained side-projection, so there's no drift to reconcile. Ownership stays 1:1: each row is written and tombstoned by exactly one object's CRDT.

```jsonc
// payloads — per-object dataset, materialized into the common space-level
// `payloads` collection via the shared-collection override (like `objects`)
{
  "id": "payload_uuid",
  "name": "report.pdf",             // human label (metadata; NOT an identity)
  "plaintextHash": "sha256-…",       // indexed; key/CID reuse for identical content
  "status": "available",             // declarative sync state (see below)

  // micro-payload (< 32 KB): inline bytes, no fileId, no filenode
  "inline": { "bytes": "base64…", "wrappedKey": "…", "mime": "image/png" },

  // OR real payload (>= 32 KB): filenode-backed, one row many variants
  "fileId": "f_uuid",                // SDK-minted, DECOUPLED from CID
  "variants": {
    "original":  { "rootCID": "bafy…", "wrappedKey": "…", "size": 4000000, "mime": "image/jpeg", "w": 4032, "h": 3024 },
    "thumbnail": { "inline": { "bytes": "base64…", "wrappedKey": "…" } }
  }
}
```

### Ownership shapes — payloads don't force a "file object", but allow one
The owner of a payload is just an object, and that cuts two ways:
- **Incidental payloads.** A page with images, an avatar on a member — the payloads are rows in the *content* object's `payloads` dataset. No per-file object is minted. This is the answer to problem #1: *don't create a file object for every small linked image.*
- **Dedicated file object.** An important standalone file (a PDF in a library, a shared document) gets a dedicated object whose purpose is to own **exactly one payload**, carrying its own `name` / type / metadata so it's a first-class, referenceable, queryable entity.

Both use the identical payloads mechanism — "file object" stops being a mandatory per-file wrapper and becomes a deliberate modeling choice. Size (inline vs filenode) is an **orthogonal** axis: a dedicated file object is usually filenode-backed, an incidental icon is usually micro-inline, but any combination is valid.

### Why this eliminates the distributed deletion race
A payload row can only be created by syncing the object that owns it. A peer **cannot observe (and therefore delete) a payload before it has seen the parent object**. If the parent is tombstoned, the payload is tombstoned with it. The CRDT's causal DAG gives lifecycle safety for free — **no space-wide reference scan, no grace-period rescue.**

### `fileId` decoupled from CID → filenode does the cross-content refcounting
`fileId` is SDK-minted (may embed `name` for readability, but **uniqueness lives on the fileId**). Decoupled from the CID, the same blocks can be bound under many fileIds; filenode refcounts per-CID (verified above), so **server-side block GC is filenode's job**. "Save the same file under three names" = three fileId bindings over one set of CIDs; deleting one leaves the blocks alive.

### Encryption — envelope, with key reuse for identical content
1. Random symmetric key **per file**. Encrypt chunks → **stable ciphertext → stable CID forever.**
2. **Reuse the same key for identical plaintext.** On create, compute `plaintextHash`, look up the index, reuse the existing key → identical ciphertext → identical CIDs → `BlocksCheck` returns `ExistsInSpace` → skip push, just `BlocksBind` the new fileId. Key+IV reuse is safe here because it is only ever across *identical* plaintext (identical ciphertext is the goal; no CFB keystream-reuse hazard).
3. Wrap the key under the **current space read key**; store the wrapped key in the variant/inline payload.
4. On ACL rotation: re-wrap only the tiny `wrappedKey` fields. **The blob on filenode is never touched.** An evicted member can no longer unwrap → loses future reads.

Do **not** derive file keys directly from the read key (ties ciphertext to the read key → rotation forces re-uploading every blob). Do **not** use convergent encryption (key = hash of plaintext) for cross-account dedup — confirmation-of-file leak. Intra-space key reuse (step 2) gets dedup without that leak (key still random per distinct content, gated behind the space read key).

### Three identifiers
| id | role | where |
|---|---|---|
| `fileId` | SDK-minted; the filenode binding id; decoupled from CID | value on the payload row |
| `plaintextHash` | intra-space key/CID-reuse key | secondary index |
| `rootCID` | network fetch address of an encrypted variant | inside `variants[*]` |

### Declarative sync — one state machine, no queue
`status` on the payload row is the whole story. The "queue" is `index WHERE status = …`.

- `pending_upload` → worker `BlockPushMany` + `BlocksBind` → `available`.
- `available` but a read finds blocks missing on filenode → downgrade to `pending_upload` and recover (self-healing; replaces anytype's unrecoverable `MissingBlocks`).
- Quota hit → `limited`; retried when `SpaceInfo` shows headroom.
- Offline create: CID computable immediately (bytes + the just-minted key); valid offline at `pending_upload`; drained on reconnect.
- Owner tombstoned → payload tombstoned → `FilesDelete(fileId)` (see ordering invariant).

Folds into the general **Sync Status** subsystem (`docs/09`), not a parallel file-status system.

### Garbage collection — server-side automatic, local-side a count query
No distributed mark-and-sweep. Two cheap mechanisms:
- **Server GC (filenode, automatic):** `FilesDelete(fileId)` on payload tombstone decrements the per-CID refcount; blocks die only when the last fileId unbinds. Cross-content sharing handled entirely server-side (verified).
- **Local block GC (a `count(*)`):** identical content shares CIDs across fileIds *locally too*, so on tombstone delete the local block for `rootCID` **only if** `count(payloads WHERE rootCID = X) == 0` **and** no queued `BlocksBind` still needs it. Instantaneous, consistent, no network. *This is the single most important invariant — see Risks.*

### Object duplication — the SDK must re-mint fileIds (future constraint)
There is **no object-copy primitive yet** in the SDK. When one is designed, it MUST be domain-aware: a generic CRDT/dataset deep-clone would copy a payload row **verbatim, including its `fileId`**, aliasing one fileId to two owners — then deleting the original `FilesDelete`s a file the copy still needs. The sanctioned copy path must detect payload rows, **strip the old `fileId`, mint a fresh one, and `BlocksBind(newFileId, sameCIDs)`** (no re-upload — blocks already exist). Record this as a hard constraint on the future copy/duplicate design.

### Network ordering invariant — never strand blocks
Offline-delete-then-recreate can queue `FilesDelete(oldFileId)` and `BlocksBind(newFileId)` for the *same* CIDs. If `FilesDelete` reaches filenode first and drops the refcount to 0, the blocks are deleted server-side; the following `BlocksBind` returns **`ErrCidsNotExist`** (verified), so the worker must re-push — **and that only works if the local blocks still exist.** Invariants:
1. **Local blocks are not deleted while any queued `BlocksBind` references their CID** (the local-GC count must include the pending-bind set).
2. Worker handles `ErrCidsNotExist` by **re-pushing from the local block store**, and prefers **bind-before-delete** ordering. If the local block is already gone *and* the server dropped it, the payload is unrecoverable — the production data-loss path to engineer against.

### Local block store — one shared DB, separate from the CRDT DB
Do **not** store 1 MB encrypted blobs in the same any-store DB as the fast-path CRDT changes and live-queried datasets: B-tree write amplification (WAL bloat, page fragmentation) thrashes the page cache and degrades live queries/UI. Decision: **one shared (account-wide) `blocks.db`** — a second any-store instance — keyed by CID, **each block row tagged with `spaceId`** so space deletion is a scan-and-delete (`DELETE WHERE spaceId = …`). (Because keys are random per file, the same plaintext in two spaces yields different CIDs, so blocks don't actually collide across spaces — the shared DB is purely a storage-location choice; the spaceId tag is what makes per-space teardown possible.) Metadata stays transactional in the per-space any-store; only block bytes go here.

### Thumbnails / variants
- **The Go SDK does NOT decode/resize images.** CPU/memory heavy, no access to iOS/Android hardware media pipelines. Host hook:
  ```go
  type MediaProcessor interface {
      GenerateVariants(ctx, raw []byte, mime string) (map[VariantKind][]byte, error)
  }
  ```
- **One payload row, many variants** — not five DAGs. All variants share one `fileId` and one lifecycle. A small variant MAY be `inline` even when `original` is on filenode, so the UI renders instantly offline while the full image streams on demand.

### Dedup — intra-space, client-side, pre-sync
- Before creating a payload, hash the plaintext, look up the index by `plaintextHash`. Hit → reuse the key/CIDs, mint a fresh fileId, `BlocksBind` (filenode refcounts). No push, no crypto compromise.
- **No cross-account server dedup** (would need convergent encryption → leaks). Accept it.
- **Accept offline-concurrent duplication** (two offline devices add the same image → different keys → different CIDs → two entries that never merge). Probability ~0; the post-sync convergence resolver to fix it is weeks of bug-prone code to save MBs. **Do not build it.**

### Why not "files as a first-class any-sync type"
Rejected. State-sync protocols optimize for tiny, causally-linked, fully-replicated mutations; file protocols optimize for large-block streaming, partial/on-demand replication, CDN caching. Forcing files into any-sync chokes metadata sync behind bulk binary and needs an expensive cross-team server change for ~0 product benefit. **Keep filenode separate; hide it behind the SDK.**

## Risks (ranked by blast radius)
1. **Local block GC / network ordering (data loss).** Deleting a local block that a queued `BlocksBind` still needs, after the server already dropped it (`ErrCidsNotExist`), is unrecoverable. The local-GC count check MUST include the pending-bind set; worker re-pushes on `ErrCidsNotExist`; prefer bind-before-delete. *#1 production risk.*
2. **Object duplication aliasing fileIds.** A future copy primitive must re-mint fileId + re-bind. A generic opaque clone is a footgun.
3. **Cascade-on-delete.** Deleting an object must tombstone *all* its payload rows in the common collection (an object can own N payloads, unlike its single `objects` row). Materialization is convergent like properties, so there's no projection drift — but the delete path must emit the per-payload tombstones.
4. **Key-reuse correctness.** Reuse the key only across *identical* plaintext (gate strictly on full `plaintextHash` + size). A partial match that reuses key+IV across *different* content breaks CFB confidentiality.

## Spike plan (chosen: prototype before committing v1 vs v1.1)
A focused spike against the local any-sync network (`~/projects/local-infra`) to de-risk before slotting files into a release:
1. **Bind/refcount round-trip:** push blocks under `fileId_A`, `BlocksBind` the same CIDs under `fileId_B` (no re-push), `FilesDelete(A)`, confirm blocks survive, `FilesDelete(B)`, confirm GC eligibility. (Validates the verified primitives end-to-end over the wire.)
2. **`payloads` materialization:** per-object `payloads` dataset wired through the shared-collection override into a common collection (like properties → `objects`); object-delete cascades tombstones to *all* its payload rows.
3. **Envelope + key-reuse dedup:** two payloads, same plaintext → same CIDs → second is bind-only.
4. **Offline ordering torture test:** offline delete + recreate of the same content; verify the `ErrCidsNotExist` → re-push-from-local path and that local GC never strands blocks.
5. **`blocks.db` perf:** thousands of 1 MB blobs in a shared blocks DB while live queries run on the metadata DB — confirm no query degradation; confirm `spaceId`-scoped delete.

Decide v1 vs v1.1 from what the spike surfaces (esp. #4 and #5).

## Sketched SDK API
```go
type Files interface {
    // Attach a payload to an EXISTING owner (the page-with-images case).
    Attach(ctx, ownerObjectId string, reader io.Reader, opts AddOpts) (PayloadRef, error)
    // CreateFileObject mints a dedicated file object owning exactly one payload
    // (the standalone-PDF case): one call -> object + its single bound payload.
    CreateFileObject(ctx, reader io.Reader, opts AddOpts) (objectId string, ref PayloadRef, err error)
    Open(ctx, fileId string, variant VariantKind) (io.ReadSeekCloser, error)
    Get(ctx, fileId string) (PayloadRecord, error)
    // Deletion is implicit: delete/tombstone the owner object (or its payload row).
}
type AddOpts struct {
    Name     string
    Mime     string
    Variants map[VariantKind][]byte // from MediaProcessor, optional
}
```
- Micro-payload path is internal: `len(bytes) < InlineThreshold (32 KB)` → inline bytes on the payload row, no `fileId`, no filenode.

## Open questions / decisions to confirm in implementation
1. **Inline threshold (32 KB):** confirm against real asset-size histograms.
2. **Shared-collection materialization:** wire `payloads` through the Controller's shared-collection override (like `SystemPropertiesHandler` → `objects`); confirm object-delete cascades tombstones to *all* the object's payload rows.
3. **Future copy primitive:** carry the "re-mint fileId + re-bind" constraint into whoever designs `DuplicateObject`.
4. **`blocks.db` shape:** confirm one shared account-wide DB + `spaceId` tag (chosen) survives the perf spike vs a per-space instance.
5. **Worker ordering:** bind-before-delete + re-push-on-`ErrCidsNotExist`; where the pending-bind set lives so local GC can consult it.
6. **Wrapped-key rotation:** who walks payloads re-wrapping keys on ACL read-key rotation; batched with the existing rotation flow.
7. **`MediaProcessor` boundary** for gomobile/wasm.
8. **Variant kinds catalog** — fixed enum vs open string.

## Dependencies
- **Space** — files live in a space; ACL/quota/encryption inherited.
- **Data structure / datasets** — per-object `payloads` dataset materialized into a common collection via the shared-collection override (like properties → `objects`); blocks in a shared `blocks.db`.
- **Sync status (`docs/09`)** — payload `status` is part of the general sync-status surface.
- **filenode** — unchanged; driven via `commonfile` RPC. No new server data type required.

## History (superseded directions)
- **v0 (rejected):** files as a first-class any-sync data type. Expensive cross-team server change; wrong workload fit; SDK-only gets the same wins with zero server changes.
- **v1 (superseded):** space-level `files` collection referenced by many objects + two-phase epoch mark-and-sweep GC with a 7-day grace to absorb a premature-deletion race. Superseded by per-object-owned `payloads` (materialized into a common collection via the shared-collection override, like properties) + SDK-minted fileId + filenode refcount, which removes the distributed mark-and-sweep entirely (the race can't occur under causal-DAG ownership) and trades it for a local `count(*)` block-GC check.
