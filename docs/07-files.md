# Files

## TL;DR — the SDK2 file model

1. **No server changes.** Keep `filenode` as a dumb, specialized, refcounted block heap. Do **not** push for "files as a native any-sync data type" — merging bulk binary into a tree-sync protocol chokes metadata sync behind gigabytes of video. The whole design lives in the SDK.
2. **One `payloads` model, two physical tiers by size.** A file payload is a record in a single space-level **`payloads` system collection**, but **owned 1:1 by exactly one object** (`owner_objectId`, tombstoned atomically with its owner).
   - **Micro-payload (< 32 KB)** — envelope-encrypted bytes inline in the payload record. No `fileId`, no filenode.
   - **Real payload (≥ 32 KB)** — chunked, envelope-encrypted, pushed to filenode; the record carries `fileId` + variants + wrapped key + status. **Not** a full any-sync object.
3. **Envelope encryption** (keep what anytype already does right): random per-file key encrypts the bytes → stable ciphertext → stable CID forever. The random key is wrapped under the space read key and stored in the payload record. ACL rotation re-wraps only the tiny key, never the blob. **Reuse the same key for identical plaintext** (found via `plaintextHash`) so identical content yields identical CIDs.
4. **`fileId` is SDK-minted and decoupled from the CID** (heart uses `fileId = root CID`). The same blocks can be bound under many fileIds; **filenode refcounts the blocks per-CID and does server-side GC for us.**
5. **The `payloads` record is the single source of truth.** Sync status is a declarative state field. Kill the separate persistent filesync queue.
6. **No distributed mark-and-sweep.** 1:1 ownership + the CRDT causal DAG make deletion safe: object tombstoned → payload dies with it → `FilesDelete(fileId)` → filenode decrements. **Local** block GC is a cheap instantaneous `count(*)` query (blocks are shared across fileIds locally), not a network operation.
7. **Thumbnails/variants are generated by the host OS, not Go.** One payload record holds many variants.
8. **Local blocks live in a SEPARATE store** (`blocks.db` / content-addressed), not the fast-path CRDT/query any-store DB.

This supersedes the earlier "files-as-first-class in any-sync, defer to v1.1" direction (kept at the bottom for history).

## What's actually below us (verified against the repos)

### any-sync `commonfile` (client chunking)
- 1 MB chunks, UnixFS balanced merkledag, **CIDv1 + SHA2-256**, codec `dag-pb`.
- **Does NO encryption.** Caller encrypts bytes *before* chunking, so **the CID is the hash of ciphertext**.
- `BlockStore`: `Get / GetMany / Add / Delete` over `blocks.Block`. `spaceId`/`fileId` flow via context.

### filenode (server)
- Stores only encrypted blocks; **zero-knowledge** of plaintext (it never re-hashes; it trusts the client's CID).
- Per-CID refcount, **dual-scoped** (per-space + per-account/"group"). Block GC'd only when refs hit zero; actual byte deletion is coordinator-driven.
- **ACL-aware:** validates `CanWrite` against the space ACL before accepting a push (`ErrForbidden` otherwise).
- Two-tier quota (account + optional per-space isolation), `ErrLimitExceed`.
- **`fileId` is distinct from CID.** The binding primitive is `BlocksBind(spaceId, fileId, []cid)`; teardown is `FilesDelete(spaceId, []fileId)`. `BlocksCheck(spaceId, []cid)` → `NotExists / Exists(account-wide) / ExistsInSpace`. **Many fileIds may bind the same CIDs; filenode refcounts them.**
- S3 (bytes) + Redis (index).
- RPCs: `BlockGet`, `BlockPush(Many)`, `BlocksCheck`, `BlocksBind`, `FilesDelete`, `FilesInfo`, `FilesGet`, `SpaceInfo`, `AccountInfo`, quota setters, `Check`.

### What anytype-heart does today (the bar to beat)
- Every file — even a 2 KB icon — is a **full first-class object** + a filenode upload. `fileId = root CID` (content-derived, so identical content can't exist as two named entities).
- Images = **5 separate variant sub-DAGs** (original/large/small/thumbnail/exif), each its own encrypted tree + key.
- **Envelope encryption already exists and is correct:** random per-file/per-variant AES-CFB key; the keys **sync with the object** (FileKeys ride in the object's changes, wrapped under the space key). The local `objectStore.AddFileKeys` table is only a fast-lookup cache, *not* the source of truth.
- Dedup: client-side, by plaintext/variant SHA-256 checksum. Random keys mean **no cross-user server dedup** (different ciphertext → different CID).
- **Sync status is a separate state machine** (`Queued→Syncing→Synced/Limited`) backed by a persistent `filesync/queue` collection, updated by async callbacks. **This is the documented root of most file bugs** — the object state and the filenode block state drift.

**The honest conclusion:** the *cryptography* anytype uses is fine. The pain is **structural** — five DAGs per image, a full object per icon, and a second consistency system (the queue + key cache) that drifts from the object. SDK2 fixes the structure, keeps the crypto.

## Design

### Principle: filenode is a dumb byte heap; the CRDT/dataset is the only source of truth
Drift happens because today the object and filenode are treated as peers coordinated by a third system (the queue). Instead: the **`payloads` record is the heap pointer**, filenode is the heap. There is exactly one source of truth and one place state is reconciled.

### The `payloads` collection — one manifest, 1:1 object-owned
A single **space-level system collection `payloads`** (implemented like the `objects` system collection: one shared collection, coalesced via a shared-collection handler), but **each record is owned by exactly one object** and written through that owner object's CRDT. When the owner is tombstoned, the CRDT sync engine **atomically tombstones the owner's payload rows**.

```jsonc
// collection: payloads  (space-level system collection, 1:1 object-owned)
{
  "id": "payload_uuid",              // payload record id
  "owner_objectId": "obj_…",         // the ONE object that owns this payload
  "name": "report.pdf",             // human label (metadata; NOT an identity)
  "plaintextHash": "sha256-…",       // indexed; key/CID reuse for identical content
  "status": "available",             // declarative sync state (see below)

  // micro-payload (< 32 KB): bytes inline, no fileId, no filenode
  "inline": { "bytes": "base64…", "wrappedKey": "…", "mime": "image/png" },

  // OR real payload (>= 32 KB): filenode-backed, one record many variants
  "fileId": "f_uuid",                // SDK-minted, DECOUPLED from CID
  "variants": {
    "original":  { "rootCID": "bafy…", "wrappedKey": "…", "size": 4000000, "mime": "image/jpeg", "w": 4032, "h": 3024 },
    "thumbnail": { "inline": { "bytes": "base64…", "wrappedKey": "…" } }  // a variant MAY be inline even when original is on filenode
  }
}
```

Why one space-level collection and not per-object datasets: the upload/GC worker must scan one place (`WHERE status = pending_upload`) — sharding payloads across N per-object datasets makes the sync loop unresilient. Why 1:1 ownership and not a shared many-referrer registry: it lets the CRDT causal DAG guarantee lifecycle safety (below), which is what kills the distributed mark-and-sweep.

### Why this eliminates the distributed deletion race
A payload row can only be created by syncing the object that owns it. So a peer **cannot observe (and therefore delete) a payload before it has seen the parent object**. If the parent is tombstoned, the payload is tombstoned with it (sticky, convergent). The 1:1 model uses the CRDT's causal DAG to make file lifecycle safety free — **no space-wide reference scan, no grace-period rescue.**

### `fileId` decoupled from CID → filenode does the cross-content refcounting
`fileId` is an SDK-minted id (may embed `name` for readability, but **uniqueness lives on the fileId**, not the name). Because it's decoupled from the CID, the same encrypted blocks can be bound under many fileIds. filenode already refcounts blocks per-CID, so **server-side block GC is filenode's job**: a block dies only when the last fileId binding it unbinds. "Save the same file under three names" = three fileId bindings over one set of CIDs; deleting one leaves the blocks alive.

### Encryption — envelope, with key reuse for identical content
1. Random symmetric key **per file**. Encrypt chunks → **stable ciphertext → stable CID forever.**
2. **Reuse the same key for identical plaintext.** On create, compute `plaintextHash`, look up an existing payload with that hash, reuse its (unwrapped) key → identical ciphertext → identical CIDs → `BlocksCheck` returns `ExistsInSpace` → skip the push, just `BlocksBind` the new fileId. Key+IV reuse is safe here because it is only ever across *identical* plaintext (no CFB keystream-reuse hazard — identical ciphertext is exactly the goal).
3. Wrap the key under the **current space read key**; store the wrapped key in the variant/inline payload.
4. On ACL rotation: re-wrap only the tiny `wrappedKey` fields inside the CRDT. **The blob on filenode is never touched.** An evicted member can no longer unwrap → loses future reads.

Do **not** derive file keys directly from the read key (ties ciphertext to the read key → rotation forces re-uploading every blob). Do **not** use convergent encryption (key = hash of plaintext) for *cross-account* dedup — it enables confirmation-of-file attacks. Intra-space key-reuse (step 2) gets dedup without that leak because the key is still random *per distinct content within the space*, gated behind the space read key.

### Three identifiers
| id | role | where |
|---|---|---|
| `fileId` | SDK-minted logical id; the filenode binding id (`BlocksBind(fileId)`); decoupled from CID | value on the `payloads` record |
| `plaintextHash` | intra-space key/CID-reuse key | secondary index on `payloads` |
| `rootCID` | network fetch address of an encrypted variant | value inside `variants[*]` |

### Declarative sync — one state machine, no queue
`status` on the `payloads` record is the whole story. The "queue" is `SELECT * FROM payloads WHERE status = …`.

- `pending_upload` → worker `BlockPushMany` + `BlocksBind` → `available`.
- `available` but a read finds blocks missing on filenode → worker downgrades to `pending_upload` and recovers (self-healing; replaces anytype's unrecoverable `MissingBlocks`).
- Quota hit → `limited`; retried when `SpaceInfo` shows headroom.
- Offline create: CID is computable immediately (bytes + the key we just minted), so the record is valid offline at `pending_upload`; the worker drains it on reconnect.
- Owner tombstoned → payload tombstoned → `FilesDelete(fileId)` (see ordering invariant).

Folds into the general **Sync Status** subsystem (`docs/09`), not a parallel file-status system.

### Garbage collection — server-side automatic, local-side a count query
There is **no distributed mark-and-sweep**. Two cheap mechanisms replace it:

- **Server GC (filenode, automatic):** `FilesDelete(fileId)` on payload tombstone decrements the per-CID refcount; blocks die only when the last fileId unbinds. Cross-content sharing handled entirely server-side.
- **Local block GC (a `count(*)`):** because identical content shares CIDs across fileIds *locally too*, when a payload is tombstoned the SDK may delete the local block for `rootCID` **only if** `SELECT count(*) FROM payloads WHERE rootCID = X` is 0 **and** no queued `BlocksBind` still needs it. Instantaneous, consistent, no network. (This is the single most important invariant — see Risks.)

### Object duplication — the SDK must re-mint fileIds
A generic CRDT/dataset deep-clone would copy a payload row **verbatim, including its `fileId`**, aliasing one fileId to two owners — then deleting the original `FilesDelete`s a file the copy still needs. **1:1 ownership must be enforced at the copy boundary:** the SDK's `DuplicateObject` must detect payload rows, strip the old `fileId`, mint a fresh one, and schedule a `BlocksBind(newFileId, sameCIDs)` (no re-upload — the blocks already exist). A generic opaque object-copy that bypasses this is a data-loss footgun and must not be the sanctioned path.

### Network ordering invariant — never strand blocks
Offline-delete-then-recreate can queue `FilesDelete(oldFileId)` and `BlocksBind(newFileId)` for the *same* CIDs. If `FilesDelete` reaches filenode first and drops the refcount to 0, the blocks are deleted server-side; a following `BlocksCheck` returns `NotExists`, so the worker must re-push — **and that only works if the local blocks still exist.** Invariants:
1. **Local blocks are not deleted while any queued `BlocksBind` references their CID** (the local-GC count check above must include the pending-bind set).
2. Prefer **bind-before-delete** ordering in the worker, or make the upload path re-push on `NotExists` from the local store. If the local block is already gone and the server dropped it, the payload is unrecoverable — this is the production data-loss path to engineer against.

### Local block store — separate from the CRDT DB
Do **not** store 1 MB encrypted blobs in the same any-store DB as the fast-path CRDT changes and live-queried datasets: B-tree write amplification (WAL bloat, page fragmentation) thrashes the page cache and degrades live queries/UI. Keep payload **metadata** transactional in any-store; put **blocks** in a separate store — a dedicated `blocks.db` (a second any-store instance is fine) or a content-addressed flat dir, keyed by CID. Space deletion drops that store wholesale. This refines the "use any-store, not flatfs" idea: any-store for metadata yes, but blocks in their *own* DB file.

### Thumbnails / variants
- **The Go SDK does NOT decode/resize images.** CPU/memory heavy, no access to iOS/Android hardware media pipelines. Expose a host hook:
  ```go
  type MediaProcessor interface {
      // host (Swift/Kotlin/web) decodes, resizes, returns variant bytes
      GenerateVariants(ctx, raw []byte, mime string) (map[VariantKind][]byte, error)
  }
  ```
- **One payload record, many variants** — not five DAGs. All variants share one `fileId` and one lifecycle. A small variant (thumbnail) MAY be `inline` even when `original` is `rootCID` on filenode, so the UI renders instantly offline while the full image streams on demand.

### Dedup — intra-space, client-side, pre-sync
- Before creating a payload, hash the plaintext and look up `payloads` by `plaintextHash`. Hit → reuse the existing key/CIDs, mint a fresh fileId, `BlocksBind` (filenode refcounts). Covers the real cases (same image in 3 notes, re-uploaded avatar). No filenode push, no crypto compromise.
- **No cross-account server dedup.** Accept it (would need convergent encryption → leaks).
- **Accept offline-concurrent duplication:** two offline devices adding the same image mint different keys → different CIDs → two filenode entries that never merge. Probability ~0; the post-sync convergence resolver to fix it is weeks of bug-prone distributed code to save MBs. **Do not build it.**

### Why not "files as a first-class any-sync type"
Rejected. State-sync protocols optimize for tiny, causally-linked, fully-replicated mutations; file protocols optimize for large-block streaming, partial/on-demand replication, CDN caching. Forcing files into any-sync chokes text/metadata sync behind bulk binary and needs an expensive cross-team server change for ~0 product benefit over the SDK-only design. **Keep filenode separate; hide it behind the SDK.**

## Risks (ranked by blast radius)
1. **Local block GC / network ordering (data loss).** Deleting a local block that a queued `BlocksBind` still needs, after the server already dropped it, is unrecoverable. The local-GC count check MUST include the pending-bind set; prefer bind-before-delete. *This is the #1 production risk.*
2. **Object duplication aliasing fileIds.** Copy must re-mint fileId + re-bind. A generic opaque clone is a footgun.
3. **Block store contention.** Blobs in the CRDT DB degrade live queries. Separate `blocks.db`.
4. **Key-reuse correctness.** Reuse the key only across *identical* plaintext (gate strictly on full `plaintextHash` + size). A hash collision or a partial match that reuses a key+IV across *different* content breaks CFB confidentiality.

## Sketched SDK API

```go
// Within a space
type Files interface {
    // Add streams bytes in, attaching the payload to an owner object.
    // Returns immediately with a fileId; CID known at once, upload async.
    Attach(ctx, ownerObjectId string, reader io.Reader, opts AddOpts) (PayloadRef, error)

    // Open streams a variant out (fetches/decrypts on demand).
    Open(ctx, fileId string, variant VariantKind) (io.ReadSeekCloser, error)

    Get(ctx, fileId string) (PayloadRecord, error)
    // Deletion is implicit: delete/tombstone the owner object (or its payload row).
}

type AddOpts struct {
    Name     string
    Mime     string
    Variants map[VariantKind][]byte // from MediaProcessor, optional
}
```

- Micro-payload path is internal: `len(bytes) < InlineThreshold (32 KB)` → inline bytes on the payload row, no `fileId`, no filenode.
- References in objects point at the payload by `fileId` (real) or read the inline bytes (micro).

## Open questions / decisions to confirm in implementation
1. **Inline threshold (32 KB):** confirm against real asset-size histograms.
2. **`payloads` as a shared-collection system dataset:** confirm it registers like `objects` (shared-collection handler) and that owner-tombstone atomically tombstones the owner's payload rows.
3. **Object-duplication interception:** is there a sanctioned `DuplicateObject` primitive, or can callers issue a generic CRDT clone that would alias fileIds? (Footgun #2 hinges on this.)
4. **Block store shape:** separate `blocks.db` any-store instance per space, one shared blocks DB, or content-addressed flat dir? Benchmark large-blob throughput vs the metadata DB.
5. **Worker ordering:** bind-before-delete vs re-push-on-NotExists; where the pending-bind set lives so local GC can consult it.
6. **Wrapped-key rotation:** who walks `payloads` re-wrapping keys on ACL read-key rotation; batched with the existing rotation flow?
7. **`MediaProcessor` boundary** for gomobile/wasm — interface that survives FFI to Swift/Kotlin/JS.
8. **Variant kinds catalog** — fixed enum vs open string.

## Source files (for reference)
- `any-sync/commonfile/fileservice/` — IPLD chunking / CID (reuse as-is).
- `any-sync/commonfile/fileproto/` — filenode dRPC (`BlocksBind`/`FilesDelete`/`BlocksCheck` are the primitives we drive).

## Dependencies
- **Space** — files live in a space; ACL/quota/encryption inherited.
- **Data structure / datasets** — `payloads` is a space-level system collection, 1:1 object-owned; blocks live in a separate local store.
- **Sync status (`docs/09`)** — payload `status` is part of the general sync-status surface.
- **filenode** — unchanged; driven via `commonfile` RPC. No new server data type required.

## History (superseded directions)

- **v0 (rejected):** files as a first-class any-sync data type (move blocks into space sync, kill filenode). Needs an expensive cross-team server change; mismatches state-sync vs block-sync workloads; SDK-only design gets the same wins with zero server changes.
- **v1 (superseded):** space-level `files` collection referenced by many objects + two-phase epoch mark-and-sweep GC with a 7-day grace period to absorb a premature-deletion race. Superseded by 1:1 object-owned `payloads` + SDK-minted fileId + filenode refcount, which removes the distributed mark-and-sweep entirely (the race can't occur under causal-DAG ownership) and trades it for a local `count(*)` block-GC check.
